algorithm note · sqrt-decomposition / bucket update

버킷 기법으로 구간 갱신과 Top-K를 동시에 잡기

N×N 격자에서 구간 전체를 더하는 연산(work)과 특정 칸의 실제 값을 읽고 쓰는 연산(get/set), 그리고 구간 내 상위 K개를 뽑는 연산(query)이 각각 최대 만 번씩 섞여서 들어온다면, 순진하게 매번 전체를 갱신하는 방식은 반드시 시간 초과가 난다. 버킷(구역) 단위로 델타를 누적해두는 아이디어 하나로 이 문제를 어떻게 풀어내는지, 주어진 소스를 한 줄씩 뜯어보며 정리한다.

01문제 상황

이 기법이 왜 필요한지부터

크기 N×N인 격자 mGrid가 주어진다. 여기에 다음 다섯 가지 연산이 섞여서, 도합 최대 10,000번 호출된다.

연산의미
init(N, K, mGrid)격자 초기화. N은 K의 배수라는 조건이 주어진다.
work(A, B, delta)A, B로 정해지는 직사각형 구간의 모든 칸에 delta를 더한다.
getLogistic(P)칸 P의 현재 값을 반환한다.
setLogistic(P, value)칸 P의 값을 value로 덮어쓴다.
query(A, B)구간 A~B 안에서 값이 큰 상위 5개 좌표를 반환한다.

여기서 문제가 슬쩍 힌트를 하나 흘려준다. work에 들어오는 A, B는 아무 좌표가 아니라 A.y % K == 0, A.x % K == 0 이고 B.y % K == K-1, B.x % K == K-1 이라는 것. 즉 A는 항상 어떤 K×K 구역의 왼쪽 위 모서리이고, B는 항상 어떤 구역의 오른쪽 아래 모서리다. 다시 말해 work가 갱신하는 범위는 항상 K×K 구역 몇 개를 딱 맞게 덮는다 — 경계가 구역 중간에서 걸치는 일이 없다. 이 조건이 전체 풀이의 자물쇠를 여는 열쇠다.

02순진한 풀이가 안 되는 이유

이중 for문으로 매번 다 갱신하면?

가장 직관적인 구현은 work(A, B, delta)가 호출될 때마다 A부터 B까지 두 번 중첩된 for문을 돌면서 mGrid[y][x] += delta를 해주는 것이다. 정확하긴 하다. 문제는 속도다.

WHY NOT

구간의 크기가 최악의 경우 N×N 전체가 될 수 있고, 이런 work가 최대 10,000번 호출된다. 총 연산량은 O(N² × 10,000). N이 조금만 커져도(예: N=1,000) 10억 × 10,000 수준으로 치솟아 시간 제한 안에 들어올 수가 없다.

반대로 getLogistic 한 번을 위해 그 칸이 지금까지 몇 번의 work에 포함됐는지 전부 되짚어보는 방식도 마찬가지로 느리다. 갱신은 빠르게, 조회도 빠르게 — 이 둘을 동시에 만족하는 구조가 필요하다.

03버킷 기법의 원리

칸 하나하나 대신, 구역 단위로 게으르게 쌓아둔다

핵심 아이디어는 단순하다. N×N 격자를 K×K 크기의 작은 버킷(구역)들로 나눈다. N이 K의 배수이므로 버킷은 (N/K) × (N/K)개가 정확히 딱 맞게 만들어진다.

그리고 work(A, B, delta)가 호출되면, 그 delta를 구간 안의 칸 하나하나에 더하는 대신 구간이 덮는 버킷들에만 더해준다. 즉 각 버킷마다 "이 구역 전체에 지금까지 얼마가 더해졌는가"를 뜻하는 bucket[by][bx] 라는 지연된 델타(lazy delta) 값을 따로 관리한다.

이렇게 하면 work 한 번의 비용은 칸의 개수가 아니라 버킷의 개수에 비례한다. 버킷이 (N/K)×(N/K)개뿐이므로, K를 √N 근방으로 잡으면 work 한 번이 O(N/K × N/K) ≈ O(N) 수준으로 줄어든다. 이 "구간을 통째로 처리하기 좋은 블록으로 미리 잘라둔다"는 접근을 흔히 제곱근 분할(sqrt decomposition)이라 부르고, 델타를 개별 원소가 아니라 구역 단위로 지연시켜 쌓아두는 방식은 세그먼트 트리의 lazy propagation과 본질적으로 같은 발상이다.

핵심

"N이 K의 배수"이고 "work의 A, B가 항상 버킷 경계"라는 두 조건이 함께 있어야만 이 트릭이 성립한다. 만약 구간이 버킷 중간에서 걸쳐 들어올 수 있다면, 걸친 버킷의 일부 칸만 델타를 받아야 하므로 버킷 델타 하나로는 표현이 안 되고 결국 칸 단위 처리로 되돌아가야 한다.

04실제 값은 어떻게 읽고 쓰는가

저장은 나눠서, 조회는 합쳐서

버킷에 델타를 몰아서 쌓아두기로 한 순간, 각 칸의 "진짜 값"은 더 이상 arr[y][x] 하나에 들어있지 않다. 진짜 값은 그 칸에 저장된 값 + 그 칸이 속한 버킷의 델타로 쪼개져 있다.

그래서 getLogistic(P)는 아주 쉽다. arr[P.y][P.x].value + bucket[해당 버킷]을 더해서 돌려주면 된다. 버킷이 몇 번 갱신됐든 상관없이 항상 O(1).

문제는 setLogistic(P, mValue)다. 만약 단순히 arr[P.y][P.x].value = mValue로 덮어써 버리면, 다음번 getLogistic이 mValue + bucket[해당 버킷]을 반환해버린다. 델타가 중복으로 한 번 더 더해지는 것이다. 이 칸은 지금까지 이 버킷이 쌓아온 델타를 "이미 반영한" 값으로 설정하고 싶은 게 아니라, 지금 이 순간의 진짜 값이 mValue가 되도록 만들고 싶은 것이므로, 저장할 때 그만큼을 미리 빼줘야 한다.

해결

arr[P.y][P.x].value = mValue - bucket[해당 버킷]로 저장한다. 그래야 다음에 get이 다시 버킷 델타를 더했을 때 정확히 mValue가 나온다.

05Top-K 조회는 "전교 5등" 문제와 같다

query()의 원리

구간 A~B 안에서 값이 큰 상위 5개를 뽑아야 한다. 이것도 그 구간에 속한 모든 칸을 매번 훑으면 느리다. 여기서 쓰는 비유가 "전교 5등을 뽑고 싶다면, 각 반의 5등까지만 모아서 그 안에서 다시 5등을 뽑으면 된다"는 것이다.

왜 이게 정확한가: 전체 상위 5개 중 어떤 버킷 하나가 기여할 수 있는 개수는 최대 5개뿐이다(전체가 5개이므로). 따라서 각 버킷의 상위 5개만 후보로 모아도, 그 후보 집합은 전체 상위 5개를 반드시 포함한다. 버킷이 여러 개 걸쳐 있어도 후보 수는 "버킷 개수 × 5" 정도로 작으므로, 그 안에서 다시 정렬해 5개를 뽑는 비용은 아주 작다.

이때 각 버킷 안에서 "값이 큰 순서"를 빠르게 꺼내기 위해, 버킷마다 정렬된 집합(TreeSet)을 미리 유지해둔다. 흥미로운 점은, work로 버킷 전체에 같은 델타가 더해져도 그 버킷 안에서의 상대적인 순위는 절대 바뀌지 않는다는 것이다(모두에게 같은 수를 더하면 대소관계는 그대로다). 그래서 TreeSet 안의 값은 델타가 반영되지 않은 "상대값" 그대로 두어도 정렬 순서는 항상 맞다 — 버킷이 갱신될 때마다 TreeSet을 다시 정렬할 필요가 없다는 뜻이다.

06주어진 소스, 한 함수씩

Object 클래스부터 work()까지

class Object implements Comparable<Object>

좌표 + 값을 함께 들고 다니는 원소. 정렬 기준을 스스로 정의한다.

@Override
public int compareTo(Object o) {
    if(this.value != o.value) return Integer.compare(o.value, this.value); // 값 내림차순
    if(this.x != o.x) return Integer.compare(this.x, o.x);                 // x 오름차순
    return Integer.compare(this.y, o.y);                                   // y 오름차순
}

값이 큰 원소가 먼저 오도록 내림차순으로 비교하고, 값이 같으면 x, 그다음 y로 동점을 깨서 완전한 전순서(total order)를 만든다. 좌표 (x, y)가 서로 다른 두 칸은 절대 compareTo가 0이 될 수 없으므로, 값이 같은 칸이 여러 개 있어도 TreeSet이 서로 다른 원소를 같은 것으로 오인해 지워버리는 일이 없다.

init(N, K, mGrid)

격자를 버킷으로 쪼개고, 버킷별 정렬 집합을 채운다.

bucketTreeSet[bucketY][bucketX].add(object);
// 이전 값을 빼지 않음(상위 5개만 관리하지 않음)
// 순위가 바뀔 때 후순위가 필요할 수도 있으니.

각 버킷의 TreeSet에는 그 버킷에 속한 모든 칸을 넣어둔다. 상위 5개만 잘라서 들고 있고 싶은 유혹이 있지만, 나중에 setLogistic으로 값이 바뀌면 6등이 5등 안으로 들어올 수도 있으므로 버킷 전체를 계속 정렬된 상태로 유지해야 한다. 대신 정렬 집합이라 삽입/삭제/조회가 모두 O(log(버킷 크기))로 싸다.

getLogistic(P)

int arrValue = arr[P.y][P.x].value;
int bucketValue = bucket[bucektY][bucketX];
return arrValue + bucketValue;

저장된 상대값과 버킷 델타를 더할 뿐이라 O(1).

setLogistic(P, mValue)

bucketTreeSet[bucektY][bucketX].remove(object);   // ① 옛 순위 제거
object.value = mValue - bucketValue;              // ② 상대값으로 환산해 저장
bucketTreeSet[bucektY][bucketX].add(object);       // ③ 새 순위로 재삽입

①③이 필요한 이유는 TreeSet이 내부적으로 compareTo 순서로 정렬돼 있기 때문이다. 값을 바꾼다는 건 정렬 위치가 바뀐다는 뜻이므로, 그냥 object.value만 고쳐서는 안 되고 지웠다가 새 값으로 다시 넣어야 정렬 구조가 깨지지 않는다. ②가 앞서 섹션 04에서 짚은, 델타 중복을 막기 위한 상대값 환산이다.

work(A, B, mDelta)

for (int x = bucketStartX; x <= bucketEndX; x++) {
    for (int y = bucketStartY; y <= bucketEndY; y++) {
        bucket[y][x] += mDelta;
    }
}

칸이 아니라 버킷을 순회한다. A, B가 항상 버킷 경계에 맞춰 들어온다는 문제 조건 덕분에 가능한 코드다. 비용은 구간이 덮는 버킷 수, 즉 O((N/K)²) — 최악이어도 전체 버킷 개수를 넘지 않는다.

query(A, B) — Top 5

for (Object object : bucketTreeSet[y][x]) {
    int realValue = object.value + bucketValue;      // 버킷 델타를 더해 "진짜 값"으로 환산
    pq.offer(new Object(object.x, object.y, realValue));
    cnt++;
    if (cnt == 5) break;                              // 버킷당 최대 5개만 후보로
}

버킷마다 상대값 순서(=진짜 값 순서, 섹션 05 참고)로 상위 5개까지만 훑어서, 그 자리에서 실제 값으로 환산한 새 객체를 후보 큐에 담는다. 이 후보들만 모아서 다시 정렬하면 구간 전체의 상위 5개가 나온다.

주의할 점

for (Object object : pq)처럼 PriorityQueue를 for-each로 그냥 순회하면, 내부 배열(힙) 순서대로 도는 것이라 정렬된 순서라는 보장이 없다. 힙은 최솟값(혹은 이 코드 기준으로는 가장 큰 진짜 값)이 루트에 있다는 것만 보장할 뿐, 나머지 원소들의 순서는 힙 구조 규칙만 지킬 뿐 전체 정렬이 아니다. 진짜로 상위 5개를 정확한 순서로 뽑으려면 pq.poll()을 5번 호출해야 한다. 아래 테스트 코드는 이 부분을 poll()로 바로잡아 구현했다 — 실제로 구현할 때 자주 놓치는 지점이니 기억해두자.

07복잡도 정리

연산순진한 방식버킷 방식
work (구간 갱신)O(N²)O((N/K)²)
getLogisticO(1)O(1)
setLogisticO(1)O(log K²)
query (Top 5)O(N² log N²)O((N/K)² · log K²)

K를 √N 근방으로 고르면 N/K도 √N 근방이 되어, work와 query 모두 O(√N) 수준의 버킷 개수만 다루게 된다. 호출이 10,000번 섞여 들어와도 총 비용이 감당 가능한 범위로 떨어지는 이유다.

08이 기법으로 만든 연습 문제

"구역 물류 센터" — 원본 소스의 문맥을 문제 형태로 재구성

PRACTICE PROBLEM

구역 물류 센터

물류 센터는 N×N 크기의 창고 그리드로 이루어져 있고, 각 칸 (y, x)에는 재고량 mGrid[y][x]가 있다. 창고는 K×K 크기의 구역 단위로 관리되며, N은 항상 K의 배수다. 다음 연산을 총 최대 10,000번 처리하라.

  • work(A, B, delta) — A~B 구역 전체 재고에 delta(음수 가능, |delta| ≤ 50,000)를 더한다. A, B는 항상 어떤 구역들의 왼쪽 위 / 오른쪽 아래 모서리로 주어진다.
  • get(P) — 칸 P의 현재 재고량을 반환한다.
  • set(P, value) — 칸 P의 재고량을 value로 고정한다.
  • query(A, B) — A~B 범위(역시 구역 경계에 맞춰 주어짐) 안에서 재고량이 가장 많은 상위 5칸의 좌표를, 재고량 내림차순(동률이면 x 오름차순, 다음 y 오름차순)으로 반환한다.

제약: 1 ≤ K ≤ N ≤ 1,000, 모든 재고량과 그 누적 합은 int 범위(±10억) 안에 들어온다.

예시 흐름
init(8, 2, grid) → work((2,2), (5,5), +10) → get((3,3)) → set((0,0), 999) → query((0,0), (7,7))

이 문제를 풀 때 스스로에게 던져야 할 질문은 정확히 이 노트에서 다룬 것들이다: delta를 칸에 바로 더질지 구역에 쌓아둘지, set에서 왜 그냥 덮어쓰면 안 되는지, top-5를 구할 때 왜 구역별 상위 5개만 모아도 충분한지.

09직접 돌려보는 테스트 케이스

버킷 구현 vs 완전탐색(brute force) — 무작위 연산을 똑같이 먹여서 결과를 비교한다

아래 실험실은 이 노트에서 설명한 버킷 자료구조와, 매번 전체를 훑는 완전탐색 구현을 동시에 만들어 같은 순서의 무작위 연산(work / get / set / query)을 흘려보낸 뒤 결과가 한 글자도 다르지 않은지 확인한다. N, K, 연산 횟수를 바꿔가며 여러 번 눌러봐도 좋다.

버킷(제곱근 분할) 기법 정리 노트 · 구간 델타 누적 + 버킷별 정렬 집합으로 갱신·조회·Top-K를 모두 O(√N) 근방에 묶는다.
