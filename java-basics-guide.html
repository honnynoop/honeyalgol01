1JDK · JRE · JVM

세 용어는 포함관계입니다: JDK ⊃ JRE ⊃ JVM. 바깥쪽으로 갈수록 "개발"에 필요한 도구가 추가됩니다.

JDK(개발도구) ⊃ JRE(실행환경) ⊃ JVM(실행엔진) — 바깥 원일수록 "만드는" 역할, 안쪽일수록 "실행하는" 역할

구성정식 명칭역할포함 요소
JVMJava Virtual Machine바이트코드(.class)를 OS에 맞춰 실행하는 가상머신클래스로더, 실행엔진, 런타임 메모리 영역
JREJava Runtime EnvironmentJVM + 실행에 필요한 표준 라이브러리(lib)JVM, 핵심 API 클래스
JDKJava Development KitJRE + 개발 도구 일체JRE, javac(컴파일러), java(실행기), javap(역어셈블), 개발용 lib/.jar

JDK의 실행파일(.exe)과 PATH

JAVA_HOME/bin에 존재하는 대표 실행파일과 역할입니다. 이 경로를 OS의 PATH 환경변수에 등록해야 어느 폴더에서든 javac, java 명령을 바로 사용할 수 있습니다.

명령어기능
javac.java 소스코드를 .class 바이트코드로 컴파일
java.class 바이트코드를 JVM 위에서 실행
javap.class 파일을 역어셈블하여 바이트코드 구조 확인(디버깅용)
JVM은 OS마다 다르게 구현됩니다. Windows JVM, Unix/Linux JVM은 내부 구현이 다르지만, 동일한 .class 바이트코드를 입력받아 각자의 방식으로 해석·실행합니다. 이것이 자바의 "Write Once, Run Anywhere"의 핵심 원리입니다 — 소스코드가 아니라 바이트코드가 이식되는 것입니다.

2컴파일과 실행과정

자바는 컴파일 언어이면서 동시에 가상머신 위에서 인터프리팅되는 하이브리드 방식입니다.

.java(사람이 읽는 소스) → javac → .class(플랫폼 독립 바이트코드) → JVM이 로드·검증·실행 → OS별 네이티브 명령으로 변환

Hello.java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, JVM!");
    }
}
터미널
$ javac Hello.java     // Hello.class 생성
$ java Hello
Hello, JVM!

.class 파일은 사람이 읽을 수 없는 바이트코드(중간언어, IL)입니다. javap -c Hello.class로 역어셈블하면 JVM 명령어(opcode) 형태를 확인할 수 있습니다.

3JVM 메모리 구조

JVM은 프로그램 실행 중 사용할 메모리를 용도에 따라 세 영역으로 나눠 관리합니다: Method Area(클래스 영역), Stack(스택 영역), Heap(힙 영역).

Method Area(공유·설계도) · Stack(스레드별·값과 참조) · Heap(공유·실제 객체, Young/Old 세대로 분리)

영역저장 내용생성 시점공유 여부
Method Area클래스 구조, static 변수, 메소드 바이트코드, 상수풀클래스 최초 로딩 시모든 스레드 공유
Stack메소드 호출 프레임, 지역변수, 매개변수, 참조형 변수의 주소값메소드 호출 시 프레임 push, 종료 시 pop스레드마다 독립
Heapnew로 생성된 모든 객체(인스턴스), 인스턴스 변수new 실행 시모든 스레드 공유
MemoryExample.java
class Fish {
    String name;   // 인스턴스 변수 → Heap
}

public class MemoryExample {
    public static void main(String[] args) {
        Fish f = new Fish();   // f: Stack(참조값) / new Fish(): Heap(실제객체)
        f.name = "Nemo";
        f = null;               // Stack의 참조를 끊음 → Heap 객체는 GC 대상이 됨
    }
}

Fish f라는 참조변수 자체는 Stack에, new Fish()로 만들어진 실제 객체는 Heap에 생성됩니다. f = null은 Stack의 참조값만 지울 뿐 Heap의 객체를 즉시 지우지 않습니다 — 더 이상 어떤 참조도 가리키지 않게 된 객체를 GC가 나중에 회수합니다.

4메모리 라이프사이클 · GC

Stack과 Heap은 서로 다른 생명주기 원칙(FILO vs GC)을 따릅니다.

Stack: FILO (First In Last Out)

메소드가 호출되면 그 메소드의 실행 정보(프레임)가 스택에 push되고, 메소드가 끝나면 pop됩니다. 가장 나중에 호출된 메소드가 가장 먼저 종료되는 후입선출 구조입니다.

StackDemo.java
public class StackDemo {
    static void a() { b(); System.out.println("a 종료"); }
    static void b() { c(); System.out.println("b 종료"); }
    static void c() { System.out.println("c 종료"); }
    public static void main(String[] args) { a(); }
}
실행결과 — push 순서: main→a→b→c, pop 순서: c→b→a→main
c 종료
b 종료
a 종료

Heap: Young Generation → GC → Old Generation

  1. 객체 생성 — 새 객체는 항상 Young Generation의 Eden 영역에 먼저 생성된다.
  2. Minor GC — Eden이 차면, 여전히 참조되고 있는(살아있는) 객체만 골라 Survivor(S0↔S1)로 이동시키고 나머지는 회수한다.
  3. 승격(Promotion) — Survivor에서 일정 횟수 이상 살아남은 객체는 Old Generation으로 이동한다.
  4. Major(Full) GC — Old Generation이 차면 발생. Minor GC보다 느리고 애플리케이션을 더 오래 멈춘다(Stop-The-World).
GC의 판단 기준은 "도달 가능성(Reachability)"입니다. 즉 어떤 참조 체인으로도 접근할 수 없게 된 객체만 회수 대상이 됩니다. Java는 C/C++와 달리 개발자가 직접 free()를 호출하지 않아도 됩니다 — 이것이 자동 메모리 관리의 핵심입니다.

5메모리 특징 4원칙

상속 관계에 있는 클래스가 클래스 로딩 → 객체 생성 → 메모리 배치 → 메소드 사용 4단계에서 각각 부모와 어떤 관계를 맺는지 정리한 4원칙입니다. 모두 "자식은 혼자 존재할 수 없고, 항상 부모를 전제로 한다"는 하나의 원리로 귀결됩니다.

1. 자생부생 — 자식이 생성되면 부모가 생성된다

new 자식()을 실행하면, 자식 생성자 본문이 실행되기 전에 반드시 부모 생성자가 먼저 호출됩니다(암묵적 super()). 즉 힙(Heap)에 자식 객체가 만들어질 때 그 내부에 부모 부분이 먼저 채워집니다 — 객체 생성 순서: 부모 → 자식.

2. 자설부설 — 자식의 설계도가 올라가면 부모의 설계도가 올라간다

클래스가 처음 사용될 때 JVM이 .class를 Method Area(설계도 영역)에 로딩하는데, 자식 클래스를 로딩하려면 부모 클래스가 먼저 로딩되어 있어야 합니다. 부모 설계도 없이는 자식 설계도가 완전할 수 없기 때문입니다 — 클래스 로딩 순서: 부모 → 자식.

3. 생주부주 — 생성된 주소는 부모의 주소다

자식 객체는 힙에 하나의 메모리 블록으로 만들어지고, 그 블록 안에 부모가 갖는 필드 영역이 포함되어 있습니다. 즉 자식 객체의 참조 주소를 통해 부모가 정의한 필드/영역까지 함께 접근할 수 있습니다 — 자식 객체 주소 = 부모 영역을 포함한 주소.

4. 설공메사 — 설계도에 공개된 메서드만 사용할 수 있다

부모 설계도(class)에 public/protected로 공개된 메소드·필드만 자식(또는 외부)이 사용할 수 있습니다. private로 감춰진 멤버는 같은 객체 메모리 안에 존재하더라도 이름으로 접근할 수 없습니다 — 캡슐화 원칙과 직결됩니다.

4원칙을 한 문장으로 요약하면: "부모의 설계도가 먼저 로딩되고(2) → 부모 생성자가 먼저 실행되어(1) → 자식 객체의 주소 자체가 부모 영역을 포함한 주소이며(3) → 그중 공개된 것만 꺼내 쓸 수 있다(4)". 이는 8장(상속)의 "부모것이 내것"과 11장(다형성)의 "부타자생·부타자참·부메자호" 원리로 이어집니다.

6OOP 4대 특징 (APIE)

객체지향 프로그래밍의 4대 특징은 앞글자를 따 APIE로 부릅니다.

약자이름한 줄 정의
AAbstraction (추상화)공통 속성·행위만 뽑아 하나의 틀(추상클래스/인터페이스)로 정의
PPolymorphism (다형성)같은 타입 참조로 서로 다른 실제 객체의 동작을 호출
IInheritance (상속)부모의 필드·메소드를 자식이 물려받아 재사용
EEncapsulation (캡슐화)내부 구현을 숨기고(private) 필요한 통로(getter/setter)만 공개

7~11장에서 이 네 가지를 순서대로 실습 코드와 함께 깊게 다룹니다.

7상속 (extends)

extends 키워드로 부모 클래스를 지정하면, 자식은 부모의 public/protected 멤버를 그대로 물려받습니다. 핵심 문장은 "부모것이 곧 내것"입니다.

삼각형 화살표는 UML 표기법에서 "상속(is-a)"을 의미 — B extends A, C extends A

Inheritance.java
class A {
    int x = 10;
    void open() { System.out.println("A.open() 호출"); }
}
class B extends A { }   // B는 x, open()을 그대로 물려받음
class C extends A { }

public class Inheritance {
    public static void main(String[] args) {
        A a1 = new A();
        B bObj = new B();
        System.out.println(bObj.x);      // 부모 필드 재사용
        bObj.open();                      // 부모 메소드 재사용
    }
}
실행결과
10
A.open() 호출
비자금(private) — "내 것도 자식한테는 안 준다"
부모의 private 멤버는 상속되지 않습니다(정확히는 자식 클래스 코드에서 직접 접근할 수 없습니다). 자식 객체 안에 메모리 공간 자체는 존재하지만, 캡슐화 원칙상 자식이 이름으로 접근할 수 없어 "물려받지 못한 것"과 같은 효과를 냅니다. 그래서 private은 흔히 "부모가 몰래 감춰둔 비자금"에 비유됩니다.
PrivateInherit.java
class Parent {
    private int secret = 1000;   // 비자금 — 자식이 직접 못 씀
    public int getSecret() { return secret; }  // 공개 통로만 허용
}
class Child extends Parent { }

public class PrivateInherit {
    public static void main(String[] args) {
        Child c = new Child();
        // System.out.println(c.secret);  // ❌ 컴파일 에러 - private
        System.out.println(c.getSecret()); // ✅ 200 - public 메소드로 접근
    }
}

8캡슐화 · 접근제어자

캡슐화는 필드는 감추고(private), 접근은 메소드로만 허용하는 설계 원칙입니다.

제어자같은 클래스같은 패키지자식 클래스(다른패키지)전체
privateOXXX
default(생략)OOXX
protectedOOOX
publicOOOO
실무 규칙: 필드는 private, 접근은 getter/setter(public)로 — 값 검증 로직을 setter 안에 넣을 수 있어 데이터 무결성을 지킬 수 있습니다.

9생성자

생성자는 "이름이 클래스명과 같고 반환타입이 없는" 특수 메소드로, new 시점에 객체를 초기화합니다. 흔히 "이름 생성자" — 클래스와 동일한 이름을 가진 생성자 — 로 요약됩니다.

Constructor.java
class Person {
    String name;
    int age;

    Person() {                 // 기본 생성자
        this("이름없음", 0);    // this()로 다른 생성자 재사용
    }
    Person(String name, int age) {  // 매개변수 생성자
        this.name = name;      // this.필드 = 매개변수 (동명이의 구분)
        this.age = age;
    }
}

public class Constructor {
    public static void main(String[] args) {
        Person p1 = new Person();
        Person p2 = new Person("홍길동", 20);
        System.out.println(p1.name + " " + p1.age);
        System.out.println(p2.name + " " + p2.age);
    }
}
실행결과
이름없음 0
홍길동 20
클래스에 생성자를 하나도 안 쓰면 컴파일러가 매개변수 없는 기본 생성자를 자동으로 넣어줍니다. 하지만 매개변수 있는 생성자를 하나라도 직접 정의하면 기본 생성자는 자동 생성되지 않으므로, 필요하면 직접 추가해야 합니다.

10오버로딩 vs 오버라이딩

오버로딩 (Overloading)오버라이딩 (Overriding)
관계같은 클래스 안부모-자식 클래스 간
이름같음같음
매개변수달라야 함(개수/타입/순서)동일해야 함
반환타입무관동일(또는 자식 타입 - 공변 반환)
목적같은 기능을 다양한 입력으로 제공부모 기능을 자식이 재정의
결정 시점컴파일 타임(정적 바인딩)런타임(동적 바인딩, VMI)
OverloadVsOverride.java
class Calc {
    void say() { System.out.println("say()"); }
    void say(int a) { System.out.println("say(int) : " + a); }  // 오버로딩
}
class SpecialCalc extends Calc {
    @Override
    void say() { System.out.println("자식이 재정의한 say()"); }  // 오버라이딩
}

public class OverloadVsOverride {
    public static void main(String[] args) {
        Calc c = new SpecialCalc();
        c.say();      // 오버라이딩된 자식 메소드 호출 (런타임 결정)
        c.say(5);     // 오버로딩된 메소드 호출 (컴파일타임 결정)
    }
}
실행결과
자식이 재정의한 say()
say(int) : 5
오버라이딩 3원칙: ① 메소드 시그니처(이름+매개변수) 동일 ② 접근제어자는 부모보다 좁힐 수 없음 ③ 예외는 부모보다 더 넓게 던질 수 없음.

11다형성 · 형변환 · VMI

다형성 발생 원리 = 반드시 상속(또는 구현) 관계여야 성립합니다. 부모 타입 참조변수가 자식 객체를 가리킬 수 있기 때문에 "하나의 타입, 여러 모습"이 가능해집니다. 이 장에서는 V(탈것)을 부모로, A(비행기) · B(버스) · C(택시)를 자식으로 하는 예제로 설명합니다.

부모 V(탈것) 타입 하나로 자식 A/B/C를 모두 가리킬 수 있고, 실제 호출되는 동작은 각 자식마다 다르다 — 이것이 다형성

다형성 발생 원리 3원칙

1. 부타자생 — 부모의 타입으로 자식을 생성할 수 있다

V v1 = new A(); — 선언 타입은 부모(V)지만, 실제로 new 되는 것은 자식(A) 객체입니다. 부모 타입 변수 하나로 원하는 자식을 골라 생성할 수 있습니다.

2. 부타자참 — 부모의 타입으로 자식을 받을 수 있다

이미 만들어진 자식 객체도 V v4 = a3;처럼 부모 타입 변수에 대입(참조)받을 수 있습니다. 메소드 매개변수가 V 타입이면 A·B·C 객체를 전부 인자로 넘길 수 있는 것도 같은 원리입니다.

3. 부메자호 — 부모의 메서드로 자식을 호출할 수 있다

부모 타입 변수 v1로 v1.move()를 호출하면, 컴파일러는 V에 move()가 있는지만 확인하고, 실제 실행되는 코드는 런타임에 힙 속 진짜 객체(A)가 오버라이딩한 버전입니다(VMI).

Vehicle.java
class V {                          // 부모: 탈것
    void move() { System.out.println("이동한다"); }
}
class A extends V {                // 자식: 비행기
    @Override void move() { System.out.println("비행기가 날아서 이동한다"); }
    void fly() { System.out.println("이륙!"); }   // A 전용 메소드
}
class B extends V {                // 자식: 버스
    @Override void move() { System.out.println("버스가 도로로 이동한다"); }
}
class C extends V {                // 자식: 택시
    @Override void move() { System.out.println("택시가 손님을 태우고 이동한다"); }
}

public class Vehicle {
    public static void main(String[] args) {
        A a3 = new A();            // 자식 타입으로 생성

        V v1 = new A();            // ① 부타자생 - 부모타입으로 자식을 생성
        V v2 = new B();            // ① 부타자생
        V v3 = new C();            // ① 부타자생
        V v4 = a3;                 // ② 부타자참 - 부모타입으로 이미 만든 자식을 받음

        v1.move();                 // ③ 부메자호 - "비행기가 날아서 이동한다" (VMI)
        v2.move();                 // ③ "버스가 도로로 이동한다"
        v3.move();                 // ③ "택시가 손님을 태우고 이동한다"
        v4.move();                 // ③ "비행기가 날아서 이동한다"

        // v1.fly();               // ❌ 컴파일 에러 - V타입 참조로는 A 전용 메소드 호출 불가
        ((A) v1).fly();            // ✅ 다운캐스팅 후 호출 가능 - "이륙!"
    }
}

VMI (Virtual Method Invocation)

V v1 = new A(); 형태로 선언해도, v1.move()를 호출하면 컴파일러가 아니라 런타임에 실제 힙에 있는 객체의 타입을 보고 어떤 move()를 실행할지 결정합니다. 이것이 가상 메소드 호출(VMI)이며, 오버라이딩이 다형성으로 이어지는 핵심 메커니즘입니다.

정리: 참조변수의 타입(V)은 "무엇을 호출할 수 있는지"(컴파일타임)를 결정하고, 실제 객체의 타입(A/B/C)은 "어떤 코드가 실행되는지"(런타임)를 결정합니다. 부타자생·부타자참·부메자호 3원칙이 바로 이 구조를 가능하게 하는 문법적 근거입니다.

13String 클래스

String은 12장에서 배운 final class의 대표 사례이자, 자바에서 가장 많이 쓰이는 참조타입입니다. char[]을 감싸고 있지만 불변(immutable)이라는 점이 다른 클래스와 근본적으로 다릅니다.

String Pool과 불변성

StringPoolDemo.java
public class StringPoolDemo {
    public static void main(String[] args) {
        String s1 = "hi";
        String s2 = "hi";
        String s3 = new String("hi");

        System.out.println(s1 == s2);        // true  - Pool의 같은 객체 참조
        System.out.println(s1 == s3);        // false - new는 Pool 밖에 새 객체
        System.out.println(s1.equals(s3));   // true  - 값 비교는 같음

        String s4 = s1 + "!";   // 문자열 연산은 매번 "새 객체" 생성 (불변이므로)
        System.out.println(s1);  // "hi" - 원본은 절대 바뀌지 않는다
        System.out.println(s4);  // "hi!"
    }
}

class Counter {
    static int count = 0;   // 모든 객체가 공유하는 카운터 (Method Area)
    int id;                  // 객체마다 따로 갖는 고유 번호 (Heap)

    Counter() {
        count++;              // 공유 변수 증가
        id = count;            // 이 시점의 count값을 내 번호로 기록
    }

    static void printCount() {           // static 메소드
        System.out.println("현재 개수: " + count);
        // System.out.println(id);        // ❌ 컴파일 에러 - static 메소드에서 인스턴스 필드 직접 사용 불가
    }
}

public class StaticDemo {
    public static void main(String[] args) {
        Counter c1 = new Counter();
        Counter c2 = new Counter();
        Counter c3 = new Counter();

        System.out.println(c1.id + " " + c2.id + " " + c3.id);  // 1 2 3 (각자 다름)
        System.out.println(Counter.count);                       // 3 (공유값, 클래스명으로 접근)
        Counter.printCount();
    }
}

class Point {
    int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }

    @Override
    public String toString() { return "Point(" + x + ", " + y + ")"; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Point)) return false;
        Point p = (Point) o;
        return this.x == p.x && this.y == p.y;
    }

    @Override
    public int hashCode() { return java.util.Objects.hash(x, y); }
}

public class ObjectMethods {
    public static void main(String[] args) {
        Point p1 = new Point(1, 2);
        Point p2 = new Point(1, 2);

        System.out.println(p1);                 // toString() 자동 호출
        System.out.println(p1 == p2);            // 주소 비교 → false
        System.out.println(p1.equals(p2));        // 값 비교(재정의) → true
        System.out.println(p1.getClass().getName());
    }
}

abstract class Animal {              // 추상클래스: 공통 필드+일부 구현 보유
    String name;
    Animal(String name) { this.name = name; }
    abstract void sound();            // 추상 메소드 - 자식이 반드시 구현
    void sleep() { System.out.println(name + " 잠잔다"); } // 공통 구현 제공
}
interface Flyable {                  // 인터페이스: 할 수 있는 행위의 약속
    void fly();                       // 추상 메소드
    default void land() { System.out.println("착지"); } // Java8+ default 구현
}

class Bird extends Animal implements Flyable {
    Bird(String name) { super(name); }
    void sound() { System.out.println(name + " 짹짹"); }
    public void fly() { System.out.println(name + " 날다"); }
}

public class AbstractVsInterface {
    public static void main(String[] args) {
        Bird b = new Bird("참새");
        b.sound();   // 추상 메소드 구현
        b.sleep();   // 추상클래스의 공통 구현 재사용
        b.fly();     // 인터페이스 구현
        b.land();    // 인터페이스의 default 메소드
    }
}

둘 다 추상화(A)와 다형성(P)의 기반입니다: 추상클래스/인터페이스 타입으로 여러 자식 객체를 통일하게 다룰 수 있고, 실제 실행은 항상 각 자식이 재정의한 메소드가 VMI로 호출됩니다.

다중 구현 예제 — 펭귄 (Penguin extends Bird implements Fish)

가장 중요한 차이 하나를 이 예제로 정리합니다: 클래스 상속(extends)은 오직 하나만 가능하지만, 인터페이스 구현(implements)은 여러 개를 동시에 할 수 있습니다. 펭귄은 "새(Bird)이면서 동시에 물고기처럼 헤엄칠 수 있는(Fish)" 존재이므로 이 둘을 함께 표현하기에 좋은 예입니다.

Penguin extends Bird2 (실선, 상속) · Penguin implements Fish (점선, 구현) — Fish는 Bird2와 같은 위(상위) 레벨에 나란히 배치, 화살표는 모두 Penguin에서 위쪽(부모/인터페이스)을 향한다

PenguinDemo.java
abstract class Animal2 {
    String name;
    Animal2(String name) { this.name = name; }
    abstract void sound();
}

abstract class Bird2 extends Animal2 {          // 추상클래스: Animal2를 딱 1개만 상속(extends)
    Bird2(String name) { super(name); }
    void layEgg() { System.out.println(name + " 알을 낳는다"); }  // 새의 공통 구현
    abstract void fly();                          // 새는 원래 날 수 있어야 하지만, 자식이 재정의하도록 추상으로 둠
}

interface Fish {                                  // 인터페이스: "헤엄칠 수 있다"는 약속
    void swim();
    default void breathe() { System.out.println("아가미 대신 폐로 숨을 참는다"); }
}

class Penguin extends Bird2 implements Fish {     // extends는 1개, implements는 여러 개 가능
    Penguin(String name) { super(name); }
    void sound() { System.out.println(name + " 꽥꽥"); }
    void fly() { System.out.println(name + "은(는) 날지 못한다"); }   // 새이지만 오버라이딩으로 예외 표현
    public void swim() { System.out.println(name + "이(가) 헤엄친다"); } // Fish 인터페이스 구현
}

public class PenguinDemo {
    public static void main(String[] args) {
        Penguin p = new Penguin("뽀로로");
        p.sound();      // Animal2에서 내려온 추상 메소드 구현
        p.layEgg();      // Bird2의 공통 구현 재사용
        p.fly();          // Bird2의 추상 메소드를 재정의(날지 못함)
        p.swim();         // Fish 인터페이스 구현
        p.breathe();      // Fish의 default 메소드

        Bird2 asBird = p;    // 부타자참 - 부모(Bird2) 타입으로 자식(Penguin)을 받음
        Fish asFish = p;      // 인터페이스 타입으로도 같은 객체를 받을 수 있음
        asBird.fly();
        asFish.swim();
    }
}

뽀로로 꽥꽥
뽀로로 알을 낳는다
뽀로로은(는) 날지 못한다
뽀로로이(가) 헤엄친다
아가미 대신 폐로 숨을 참는다
뽀로로은(는) 날지 못한다
뽀로로이(가) 헤엄친다
핵심 포인트 3가지
① Penguin은 extends를 단 하나(Bird2)만 쓸 수 있지만, implements는 Fish 외에도 implements Fish, Swimmable, Trainable처럼 콤마로 여러 개 나열할 수 있습니다.
② 부모(Bird2)가 정의한 추상 메소드(fly())를 자식이 "새답지 않게" 재정의할 수 있는 것도 오버라이딩의 자유입니다 — 다형성은 "펭귄답게" 동작을 바꾸는 것을 허용합니다.
③ 같은 Penguin 객체를 Bird2 타입으로도, Fish 타입으로도 받을 수 있는 것이 11장의 부타자참 원리이며, 인터페이스가 있기에 상속 트리와 무관한 타입으로도 다형성을 확장할 수 있습니다.

18메모리 종합 다이어그램 — A a1 = new A();

지금까지 배운 Method Area(설계도) · Heap(실제 객체) · Stack(참조), 상속 계층(A extends V extends Object), Object의 hashCode()를 하나의 그림으로 통합합니다. A a1 = new A(); 한 줄이 실행되는 순간 세 영역에서 각각 무슨 일이 일어나는지 원(circle) 레이어로 표현했습니다.

Method Area(왼쪽)의 설계도 O→V→A 순서로 로딩된 뒤, new A()가 Heap(오른쪽)에 그 설계도 그대로 O⊂V⊂A 구조의 실제 객체를 만들고, Stack의 참조변수 a1은 그 객체의 Object 영역(hashCode)을 가리킨다.

A_V_Object.java
class V { void move() { System.out.println("이동한다"); } }   // Object를 암묵적으로 extends
class A extends V { void open() { System.out.println("A.open()"); } }

public class A_V_Object {
    public static void main(String[] args) {
        A a1 = new A();   // Method Area: O→V→A 설계도가 이미 로딩되어 있음
                            // Heap: O를 포함한 V를 포함한 A 객체 1개 생성
                            // Stack: 참조변수 a1이 그 Heap 객체의 주소를 저장
        System.out.println(a1.hashCode());   // Object가 제공하는 고유 식별값
        System.out.println(a1);              // Object.toString() 기본형: 클래스명@16진수hashCode
    }
}
실행결과 (실제 값은 실행마다 다름)
439288016
A@1a2b3c4d
이 그림이 5장(메모리 특징 4원칙)과 만나는 지점: 자설부설(Method Area에 O→V→A 순서로 설계도 로딩) → 자생부생(Heap에 O→V→A 순서로 생성자 실행) → 생주부주(Heap에 만들어진 하나의 주소 안에 A뿐 아니라 V, Object 영역까지 포함) → 설공메사(a1로는 A·V·Object 중 공개된 멤버만 호출 가능). hashCode()는 그중 Object가 공개한 대표적인 메소드입니다.

19참조타입 vs 실제타입 다이어그램 — V v1 = new A();

18장과 같은 구조이지만, 이번에는 참조변수의 선언 타입(V)과 실제 생성된 객체의 타입(A)이 다릅니다. 11장의 다형성(부타자생)이 메모리 위에서 어떻게 그려지는지 확인합니다.

Method Area에는 v1의 선언 타입(V) 기준 설계도(O→V)만 표시 — 실제로는 A의 설계도도 이미 로딩되어 있지만, v1이 "알고 있는" 범위는 V까지다. Heap에는 실제 생성된 A 객체가 O⊂V⊂A 구조 그대로 만들어지고, Stack의 v1은 그 객체의 Object 영역을 참조한다.

V_v1_new_A.java
class V { void move() { System.out.println("V.move()"); } }         // Object를 암묵적으로 extends
class A extends V { void move() { System.out.println("A.move()"); } void open() { System.out.println("A.open()"); } }

public class V_v1_new_A {
    public static void main(String[] args) {
        V v1 = new A();     // 선언 타입 V, 실제 객체 A (부타자생 - 11장)
                              // Method Area: v1은 V→Object 설계도까지만 "보인다"
                              // Heap: 실제로는 A 전체(O⊂V⊂A)가 만들어짐
                              // Stack: 참조변수 v1이 그 객체를 가리킴

        v1.move();             // "A.move()" - 실제 객체(A) 기준으로 VMI 실행 (부메자호)
        // v1.open();          // ❌ 컴파일 에러 - V타입 참조로는 A 전용 메소드 호출 불가
        System.out.println(v1.hashCode());   // Object가 제공하는 고유 식별값
    }
}
실행결과 (해시값은 실행마다 다름)
A.move()
439288016
18장과의 차이: A a1 = new A()는 선언 타입과 실제 타입이 같아 Method Area에 A까지 보였지만, V v1 = new A()는 선언 타입이 V이므로 Method Area에는 V까지만 표시했습니다. 그러나 Heap에 만들어지는 실제 객체는 두 경우 모두 동일하게 O⊂V⊂A 전체입니다 — 이것이 "타입은 컴파일타임에 호출 가능 범위를 제한하지만, 실행은 항상 런타임의 진짜 객체를 따른다"는 다형성의 핵심(11장 VMI)입니다.

20종합 체크리스트

  • JDK ⊃ JRE ⊃ JVM 포함관계와 각 구성요소(javac/java/javap)를 설명할 수 있다
  • .java → .class(바이트코드) → JVM 실행 흐름을 그릴 수 있다
  • Method Area(공유·설계도) / Stack(스레드별·FILO) / Heap(공유·GC대상)의 역할을 구분한다
  • Young Generation(Eden/S0/S1) → Old Generation 승격과 Minor/Major GC 차이를 안다
  • OOP 4대 특징 APIE(추상화/다형성/상속/캡슐화)를 각각 예시로 설명할 수 있다
  • 상속에서 private 멤버는 물려받지 못한다는 것과 그 이유(캡슐화)를 안다
  • 생성자의 특징(이름=클래스명, 반환타입 없음, this()/super() 사용법)을 안다
  • 오버로딩(같은 클래스·매개변수 다름·컴파일타임)과 오버라이딩(부모자식·시그니처 동일·런타임)을 구분한다
  • 다형성 3원칙(부타자생·부타자참·부메자호)과 업캐스팅/다운캐스팅, VMI(실제 객체 기준 메소드 호출)를 설명할 수 있다
  • final 변수/메소드/클래스의 차이와 String이 final class인 이유를 안다
  • String Pool과 불변성(== vs equals()) 및 주요 메서드(substring/split/trim 등)를 안다
  • static 멤버가 Method Area에 저장되어 모든 인스턴스가 공유한다는 것과 static 메소드의 제약을 안다
  • Object의 toString/hashCode/equals/getClass 기본 동작과 재정의 이유를 안다
  • equals() 재정의 시 hashCode()도 함께 재정의해야 하는 이유를 설명할 수 있다
  • A a1 = new A(); 한 줄이 Method Area(O→V→A 설계도) · Heap(O⊂V⊂A 실제객체) · Stack(참조 a1) 세 영역에서 어떻게 처리되는지 그림으로 설명할 수 있다
  • V v1 = new A(); 처럼 선언 타입과 실제 타입이 다를 때, Method Area(선언타입 기준)와 Heap(실제타입 기준)의 차이를 그림으로 설명할 수 있다
  • 추상클래스(is-a, 부분구현)와 인터페이스(can-do, Java8+ default) 차이를 안다
  • Penguin extends Bird implements Fish처럼 extends는 1개만, implements는 여러 개 가능함을 UML로 설명할 수 있다
