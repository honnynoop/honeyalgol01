왜 마방진에 이렇게 많은 패턴을 적용할 수 있을까?

마방진은 "① 알고리즘으로 생성 ② 검증 ③ 출력"이라는 단순한 흐름이지만, 이 각 단계마다 "생성을 어떻게 유연하게 할까", "검증 결과를 누구에게 알릴까", "출력 방식을 어떻게 확장할까" 같은 전형적인 설계 고민이 그대로 들어맞아 GoF 패턴 대부분을 자연스럽게 적용해볼 수 있습니다.

1. Singleton Pattern — 마방진 공장은 하나면 충분하다

마방진을 만들어주는 "공장"은 내부에 상태(데이터)를 갖지 않는 순수한 로직 덩어리입니다. 이런 객체를 여러 개 만들 이유가 없으므로, 애플리케이션 전체에서 단 하나의 인스턴스만 존재하도록 강제합니다.

생성 패턴이전 학습서 s120의 FactoryMagic 정식 소개
의도(Intent) 클래스의 인스턴스가 오직 하나만 만들어지도록 보장하고, 그 인스턴스에 접근할 수 있는 전역 진입점을 하나 제공한다.
// UML — Singleton
private 생성자가 외부의 new를 막고, static 필드 하나가 유일한 인스턴스를 붙잡고 있습니다. 그림에서 화살표는 "자기 자신을 가리키는 자기 참조(self-reference)"를 뜻합니다.
Java — FactoryMagic.java (지연 초기화 방식)
3요소: private 생성자 + static 필드 + static 진입점

public class FactoryMagic {
    private static FactoryMagic ins;    // ① 유일 인스턴스를 담을 static 필드

    private FactoryMagic() { }           // ② 생성자를 private로 막아 외부의 new 차단

    public static FactoryMagic getInstence() {  // ③ 유일한 진입점
        if (ins == null) {                 // 아직 안 만들어졌으면
            ins = new FactoryMagic();       // 최초 1회만 생성
        }
        return ins;                       // 이후 호출은 항상 같은 객체 반환
    }
}

class FactoryMagic:
    _instance = None              # ① 유일 인스턴스를 담을 클래스 변수

    def __new__(cls):            # ② 생성 자체를 가로채는 매직 메서드
        if cls._instance is None:

        return cls._instance         # 이후 호출은 항상 같은 객체 반환

2. Factory Method Pattern — "어떤 마방진을 만들지"를 한 곳에 모으기

클라이언트가 n % 2, n % 4를 직접 계산해서 OddMagicSquare/FourMagicSquare/SixMagicSquare 중 하나를 new하면, 새로운 마방진 종류가 추가될 때마다 클라이언트 코드를 전부 찾아 고쳐야 합니다. Factory Method는 이 "생성 로직"을 한 메서드 안에 캡슐화합니다.

생성 패턴이전 학습서 s120의 FactoryMagic.getMagicSquare(n) 정식 소개
의도(Intent) 객체를 생성하는 인터페이스(또는 메서드)를 정의하되, 어떤 클래스의 인스턴스를 만들지는 서브클래스(또는 조건 분기)가 결정하게 한다. new 키워드를 코드 곳곳에 흩어놓지 않고 한 곳으로 모은다.
// UML — Factory Method
<<create>> 화살표는 "이 메서드가 저 클래스를 생성한다"는 의미의 의존 관계입니다. 클라이언트는 FactoryMagic만 알면 되고 세 구체 클래스의 이름을 몰라도 됩니다.
Java — 팩토리 메서드가 없을 때 vs 있을 때
before / after 비교
// ────────── BEFORE: 클라이언트가 직접 분기 (Factory Method 없음) ──────────
IMagicSquare magic;
if (n % 2 != 0) {
    magic = new OddMagicSquare(n);      // 클라이언트가 구체 클래스를 직접 알아야 함
} else if (n % 4 == 0) {
    magic = new FourMagicSquare(n);
} else {
    magic = new SixMagicSquare(n);
}
// → 새 마방진 종류가 추가될 때마다 이 분기문이 있는 모든 곳을 찾아 수정해야 함

// ────────── AFTER: Factory Method로 분기를 한 곳에 모음 ──────────
public class FactoryMagic {
    public IMagicSquare getMagicSquare(int n) throws MagicException {
        IMagicSquare im = null;
        if (n <= 2) {
            throw new MagicException("2보다 작은 수의 마장진은 ");
        }
        if (n % 2 != 0) {
            im = new OddMagicSquare(n);       // ★ 생성 로직이 이 메서드 안에만 존재
        } else if (n % 4 == 0) {
            im = new FourMagicSquare(n);
        } else {
            im = new SixMagicSquare(n);
        }
        return im;
    }
}

// 클라이언트는 이제 이렇게만 호출한다 — 구체 클래스 이름 몰라도 됨
IMagicSquare magic = new FactoryMagic().getMagicSquare(n);

# Python다운 대안 ①: 딕셔너리 기반 팩토리 (if-else 없이 등록/조회로 확장)
class RegistryFactory:
    _registry = {}                       # {판별함수: 생성클래스} 매핑

    @classmethod
    def register(cls, predicate, klass):
        cls._registry[predicate] = klass  # 새 종류를 "등록"만 하면 됨 — if-else 수정 불필요

    @classmethod
    def create(cls, n):
        for predicate, klass in cls._registry.items():
            if predicate(n):
                return klass(n)
        raise MagicException(str(n))

RegistryFactory.register(lambda n: n % 2 != 0, OddMagicSquare)
RegistryFactory.register(lambda n: n % 4 == 0, FourMagicSquare)
RegistryFactory.register(lambda n: n % 4 == 2, SixMagicSquare)
magic = RegistryFactory.create(7)   # OCP를 더 잘 지키는 확장형 팩토리

3. Strategy Pattern — 생성 알고리즘을 교체 가능한 객체로

상속 대신 합성(composition)으로 알고리즘을 갈아끼웁니다. 마방진 컨텍스트는 "어떻게 만드는지"를 몰라도 되고, 실행 중에도 알고리즘을 바꿀 수 있습니다.

행동 패턴has-a 관계 (상속 아님)
의도(Intent) 동일한 문제를 푸는 여러 알고리즘군을 정의하고, 각각을 캡슐화해서 서로 교체 가능하게 만든다. 클라이언트는 어떤 알고리즘이 쓰이는지 몰라도 된다.
// UML — Strategy
Context는 인터페이스(MagicAlgorithm)를 필드로 소유하고, 세 전략 클래스는 그 인터페이스를 실현(구현)합니다. 상속 트리가 아니라 "부품을 갈아끼우는" 구조입니다.
Java
MagicAlgorithm.java / 3 Strategy / Context
public interface MagicAlgorithm {
    int[][] generate(int n);   // 알고리즘의 공통 규약
}

public class OddStrategy implements MagicAlgorithm {
    public int[][] generate(int n) {
        int[][] magic = new int[n][n];
        int x = 0, y = n/2;
        for (int i = 1; i <= n*n; i++) { /* 나선 배치 알고리즘 (이전 학습서 참조) */ }
        return magic;
    }
}
public class FourStrategy implements MagicAlgorithm {
    public int[][] generate(int n) { /* LUX 반전법 */ return new int[n][n]; }
}
public class SixStrategy implements MagicAlgorithm {
    public int[][] generate(int n) { /* makeA~makeOdd 5단계 */ return new int[n][n]; }
}

public class MagicSquareContext {
    private MagicAlgorithm algorithm;   // ★ 알고리즘을 "필드"로 보유 (상속 아님)
    private int[][] magic;

    public MagicSquareContext(MagicAlgorithm algorithm) {
        this.algorithm = algorithm;      // 생성 시점에 전략 주입 (DI)
    }

        magic = algorithm.generate(n);      // 위임(delegation) — 실제 작업은 전략에게
    }
    public int[][] getMagic() { return magic; }
}

4. Template Method Pattern — 고정된 골격, 교체 가능한 부분만 오버라이딩

이전 학습서 s117의 SixMagicSquare가 이미 makeA→makeB→makeCD→makeMulti→makeOdd 순서를 갖고 있었습니다. 이 "고정된 순서"를 부모 클래스가 강제하고, 각 단계만 자식이 채우도록 재구성한 것이 Template Method입니다.

행동 패턴s117 SixMagicSquare 알고리즘을 재구조화
의도(Intent) 알고리즘의 골격(뼈대)을 부모 클래스의 메서드 하나에 고정하고, 알고리즘의 일부 단계만 자식 클래스가 오버라이딩하게 한다. "무엇을 언제 실행할지"는 부모가 결정하고 "어떻게 할지"만 자식이 결정한다.
// UML — Template Method
부모의 make()는 final(재정의 금지) — 실행 순서 자체는 절대 바뀌지 않고, fillPattern()같은 훅(hook) 메서드만 자식이 바꿉니다.
Java — MagicSquareTemplate.java

public abstract class MagicSquareTemplate {
    protected int[][] magic;
    protected int n;

    public final int[][] make(int n) {  // ★ final — 자식이 순서를 바꿀 수 없음
        this.n = n;
        magic = new int[n][n];
        initialize();              // 훅 ① — 기본은 아무 것도 안 함
        fillPattern();             // 추상 ② — 반드시 자식이 구현
        if (needsPostProcessing()) {  // 훅 ③ — 기본은 false
            postProcess();          // 훅 ④ — 필요한 자식만 오버라이딩
        }
        return magic;
    }
    protected void initialize() { }              // 기본 구현 있는 훅(선택적 오버라이딩)
    protected abstract void fillPattern();      // 반드시 오버라이딩해야 하는 단계
    protected boolean needsPostProcessing() { return false; }  // 기본값 false
    protected void postProcess() { }
}

    private void makeOdd(){ /* ... */ }

from abc import ABC, abstractmethod

class MagicSquareTemplate(ABC):
    def __init__(self):
        self.magic = None
        self.n = 0

    def make(self, n):        # Python엔 final 키워드가 없다 —
                              # "오버라이딩하지 말라"는 의도를 문서화(docstring)로 표시

        pass

5. Builder Pattern — 옵션이 많은 마방진을 단계별로 조립

크기, 종류(자동판별 여부), 라벨, 배수(scale) 등 옵션이 늘어날수록 생성자 하나로는 감당이 안 됩니다. Builder는 메서드 체이닝으로 필요한 옵션만 순서 없이 설정하고 마지막에 build()로 완성합니다.

생성 패턴긴 생성자 대신 fluent API
의도(Intent) 복잡한 객체의 생성 과정을 단계별로 분리해서, 같은 절차로도 서로 다른 표현(결과물)을 만들 수 있게 한다. 매개변수가 많은 생성자(telescoping constructor) 문제를 해결한다.

6. Prototype Pattern — 알고리즘 재실행 없이 복제해서 재사용

n이 커질수록(예: 100x100) 생성 알고리즘이 오래 걸릴 수 있습니다. 이미 만든 마방진을 깊은 복사(deep copy)로 복제해두면, 값을 실험적으로 바꿔봐도 원본과 알고리즘 재실행 비용에 영향을 주지 않습니다.

생성 패턴deep copy로 "생성"을 대체
의도(Intent) 생성 비용이 큰 객체를 매번 새로 만드는 대신, 이미 만들어진 인스턴스를 복제(clone)해서 재사용한다. 복제 시 내부의 참조형 필드(2차원 배열)까지 독립되게 깊은 복사해야 한다.
// UML — Prototype
Java — OddMagicSquare에 clone() 추가
Cloneable + Object.clone() 오버라이딩
2차원 배열은 얕은 복사가 되므로 직접 깊은 복사 필요
public class OddMagicSquare extends MagicSquare implements Cloneable {
    public OddMagicSquare(int n) { super(n); }

    @Override
    public OddMagicSquare clone() {
        try {
            OddMagicSquare copy = (OddMagicSquare) super.clone();  // 얕은 복사(필드 값만 복사)
            copy.magic = new int[n][n];               // ★ 배열은 직접 새로 만들어야 함
            for (int i = 0; i < n; i++)
                copy.magic[i] = magic[i].clone();       // 행 단위로 깊은 복사
            return copy;
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);       // Cloneable을 구현했으므로 절대 발생 안 함
        }
    }
}

import copy

class OddMagicSquare(MagicSquare):

    def clone(self):
        return copy.deepcopy(self)   # ★ deepcopy가 2차원 리스트까지 재귀적으로 복사

    # 세밀한 제어가 필요하면 __deepcopy__를 직접 구현할 수도 있음
    def __deepcopy__(self, memo):

        new_obj._magic = [row[:] for row in self._magic]  # 행 단위 슬라이싱 복사
        return new_obj

7. Decorator Pattern — 원본을 고치지 않고 출력 기능을 덧씌우기

테두리 출력, 통계(합계/최대/최소) 출력, 강조 색상 출력을 매번 MagicSquare 클래스 안에 if문으로 추가하면 클래스가 비대해집니다. Decorator는 같은 인터페이스를 구현하는 겹겹이 감싸는 래퍼로 기능을 조합합니다.

구조 패턴원본 클래스 무수정 (OCP 준수)
의도(Intent) 객체에 부가 기능을 동적으로 추가한다. 상속으로 기능을 늘리면 조합이 폭증하지만(테두리+통계+색상 = 2³ 서브클래스), Decorator는 필요한 것만 겹쳐서 조합할 수 있다.
// UML — Decorator
MagicDecorator는 IMagicSquare를 구현하면서 동시에 다른 IMagicSquare를 필드로 감쌉니다(자기 자신과 같은 타입을 포함) — 이것이 Decorator의 핵심 구조입니다.
Java — MagicDecorator 계층
추상 데코레이터 + 2개의 구체 데코레이터
public abstract class MagicDecorator implements IMagicSquare {
    protected IMagicSquare wrapped;         // ★ 자기 자신과 같은 타입을 감싼다
    public MagicDecorator(IMagicSquare wrapped) { this.wrapped = wrapped; }

    public void make() { wrapped.make(); }   // 기본은 그대로 위임(delegation)
    public void print() { wrapped.print(); }  // 각 데코레이터가 필요한 부분만 오버라이딩
}

public class BorderDecorator extends MagicDecorator {
    public BorderDecorator(IMagicSquare wrapped) { super(wrapped); }
    @Override
    public void print() {
        System.out.println("┏━━━━━━━━━━━━━━━┓");  // 부가 기능: 테두리 추가
        wrapped.print();                             // 원본 출력은 그대로 위임
        System.out.println("┗━━━━━━━━━━━━━━━┛");
    }
}

public class StatisticsDecorator extends MagicDecorator {
    public StatisticsDecorator(IMagicSquare wrapped) { super(wrapped); }
    @Override
    public void print() {
        wrapped.print();
        int[][] m = ((MagicSquare) wrapped).getMagic();
        int sum=0, max=Integer.MIN_VALUE;
        for (int[] row : m) for (int v : row) { sum+=v; max=Math.max(max,v); }
        System.out.println("합계="+sum+", 최댓값="+max);  // 부가 기능: 통계 추가
    }
}

// 사용 예 — 필요한 데코레이터만 겹겹이 감싸기

decorated.make();
decorated.print();  // 테두리 + 원본 출력 + 통계까지 한 번에
같은 인터페이스로 감싸기위임 + 부가기능
Python — 데코레이터 클래스 (파이썬 @데코레이터 문법과는 다름)
주의: 여기서는 GoF 패턴, @문법 데코레이터가 아님
class MagicDecorator:
    def __init__(self, wrapped):
        self._wrapped = wrapped        # ★ 같은 역할의 객체를 감싼다

    def make(self):
        self._wrapped.make()           # 기본 위임

    def print(self):
        self._wrapped.print()


class BorderDecorator(MagicDecorator):
    def print(self):
        print("┏━━━━━━━━━━━━━━━┓")     # 부가 기능
        self._wrapped.print()
        print("┗━━━━━━━━━━━━━━━┛")


class StatisticsDecorator(MagicDecorator):
    def print(self):
        self._wrapped.print()
        flat = [v for row in self._wrapped.magic for v in row]
        print(f"합계={sum(flat)}, 최댓값={max(flat)}")  # 부가 기능


# 사용 예 — 함수 합성처럼 자유롭게 감싸기
sq = OddMagicSquare(5)
decorated = StatisticsDecorator(BorderDecorator(sq))  # 원하는 순서로 조합
decorated.make()
decorated.print()   # 테두리 + 원본 출력 + 통계

8. Facade Pattern — 복잡한 내부를 한 번의 호출로 감추기

지금까지 FactoryMagic, MagicException, MagicPrint, try-with-resources를 모두 알아야 마방진 하나를 만들 수 있었습니다. Facade는 이 모든 것을 단 하나의 정적 메서드 뒤로 숨겨서 초보 사용자도 쉽게 쓰게 합니다.

구조 패턴단순한 창구(단일 진입점) 제공
의도(Intent) 여러 서브시스템(팩토리, 예외처리, 출력, 자원관리)에 대한 통합된 상위 인터페이스를 제공해서, 클라이언트가 세부사항을 몰라도 쉽게 쓸 수 있게 한다.
// UML — Facade
Client는 이제 MagicFacade.create(n) 하나만 알면 되고, 내부에서 어떤 서브시스템이 어떤 순서로 협력하는지는 신경 쓰지 않습니다.
Java — MagicFacade.java
4개 서브시스템을 하나의 정적 메서드로 통합
public class MagicFacade {
    // 서브시스템: FactoryMagic(생성) + MagicException(예외) + MagicPrint(출력) + try-with-resources(자원관리)
    public static IMagicSquare create(int n) {
        try (FactoryMagic factory = FactoryMagic.getInstence()) {  // ① 자원 관리
            IMagicSquare magic = factory.getMagicSquare(n);           // ② 생성 위임
            MagicPrint.print(magic);                                 // ③ 출력까지 한 번에
            return magic;
        } catch (MagicException e) {                                // ④ 예외까지 내부에서 처리
            System.out.println("마방진을 만들 수 없습니다: " + e.getMessage());
            return null;
        } catch (Exception e) {
            return null;
        }
    }
}

// 사용 예 — 이전에는 4개 클래스를 알아야 했지만 이제는 한 줄
IMagicSquare sq = MagicFacade.create(7);   // 생성+검증+출력+예외처리+자원정리 전부 완료
단일 진입점서브시스템 통합
Python — magic_facade.py
모듈 레벨 함수로도 충분히 Facade를 표현 가능
class MagicFacade:
    @staticmethod
    def create(n):
        try:
            with FactoryMagic() as factory:      # ① 자원 관리(컨텍스트 매니저)
                magic = factory.get_magic_square(n)  # ② 생성 위임
                MagicPrint.print_magic(magic)        # ③ 출력
                return magic
        except MagicException as e:          # ④ 예외 처리
            print(f"마방진을 만들 수 없습니다: {e}")
            return None


# Python다운 대안: 클래스 없이 모듈 함수 하나로도 Facade 역할이 충분함
def create_magic(n):
    try:
        with FactoryMagic() as factory:
            magic = factory.get_magic_square(n)
            MagicPrint.print_magic(magic)
            return magic
    except MagicException as e:
        print(f"마방진을 만들 수 없습니다: {e}")
        return None


# 사용 예
sq = MagicFacade.create(7)   # 한 줄로 생성+검증+출력+예외처리 완료
@staticmethod 또는 모듈 함수
Facade vs Factory Method 차이 s120의 FactoryMagic은 "어떤 클래스를 생성할지"만 책임지는 생성 전담 패턴이고, Facade는 그 생성 로직을 포함해 출력·예외처리·자원관리까지 통째로 감싸는 더 상위의 창구입니다. Facade 내부에서 Factory Method를 그대로 사용하는 것이 일반적입니다.

9. Observer Pattern — 마방진 완성을 여러 곳에 동시에 통보

마방진이 만들어지면 콘솔에 로그를 남기고, 통계를 수집하고, 검증 실패시 알림을 보내야 할 수 있습니다. Observer는 주체(발행자)가 구독자 목록을 들고 있다가 이벤트 발생 시 모두에게 통지하는 구조입니다.

행동 패턴발행-구독(pub-sub) 구조
의도(Intent) 한 객체(주체)의 상태가 변할 때, 그 객체에 의존하는 여러 객체(관찰자)들에게 자동으로 알림이 가도록 일대다(one-to-many) 의존 관계를 정의한다.
// UML — Observer
Subject는 관찰자들을 인터페이스 타입의 리스트로만 알고 있어서, 구체적으로 몇 개의 어떤 관찰자가 붙어있는지 신경 쓰지 않고 통지만 하면 됩니다.
Java — MagicObserver / Subject
public interface MagicObserver {
    void onGenerated(int[][] magic, boolean valid);  // 통지받을 규약
}

public class ConsoleLogger implements MagicObserver {
    public void onGenerated(int[][] magic, boolean valid) {
        System.out.println("[LOG] 마방진 생성 완료, 유효성=" + valid);
    }
}

public class StatCollector implements MagicObserver {
    private int successCount = 0, failCount = 0;
    public void onGenerated(int[][] magic, boolean valid) {
        if (valid) successCount++; else failCount++;   # 통계만 조용히 누적
    }
}

public class MagicSquareSubject {
    private List<MagicObserver> observers = new ArrayList<>();  // ★ 인터페이스 타입 리스트로 보유

    public void addObserver(MagicObserver o) { observers.add(o); }  // 구독

    public void generateAndNotify(IMagicSquare magic) {
        magic.make();
        boolean valid = ((MagicSquare) magic).isMagicPublic();  // 검증 결과
        for (MagicObserver o : observers) {
            o.onGenerated(magic.getMagic(), valid);   // ★ 등록된 모두에게 통지(broadcast)
        }
    }
}

// 사용 예
MagicSquareSubject subject = new MagicSquareSubject();
subject.addObserver(new ConsoleLogger());     // 구독자 ①
subject.addObserver(new StatCollector());    // 구독자 ②
subject.generateAndNotify(new OddMagicSquare(5));  // 둘 다 동시에 통지받음
발행-구독일대다 통지
Python — 옵저버, 콜백 함수로도 대체 가능
from abc import ABC, abstractmethod

class MagicObserver(ABC):
    @abstractmethod
    def on_generated(self, magic, valid): ...

class ConsoleLogger(MagicObserver):
    def on_generated(self, magic, valid):
        print(f"[LOG] 마방진 생성 완료, 유효성={valid}")

class StatCollector(MagicObserver):
    def __init__(self):
        self.success = self.fail = 0
    def on_generated(self, magic, valid):
        if valid: self.success += 1
        else: self.fail += 1


class MagicSquareSubject:
    def __init__(self):
        self._observers = []           # ★ 구독자 목록

    def add_observer(self, observer):
        self._observers.append(observer)

    def generate_and_notify(self, magic):
        magic.make()
        valid = magic.is_magic()       # 검증 결과
        for o in self._observers:
            o.on_generated(magic.magic, valid)   # 모두에게 통지


# Python다운 대안: 클래스 없이 콜백 함수 리스트로도 옵저버 구현 가능
class SimpleSubject:
    def __init__(self):
        self._callbacks = []
    def on(self, fn):            # 데코레이터 스타일 구독
        self._callbacks.append(fn)
    def notify(self, *args):
        for fn in self._callbacks: fn(*args)


# 사용 예
subject = MagicSquareSubject()
subject.add_observer(ConsoleLogger())
subject.add_observer(StatCollector())
subject.generate_and_notify(OddMagicSquare(5))
ABC 인터페이스콜백 함수 리스트로 대체 가능
Observer 구성요소역할
Subject (발행자)상태 변화를 감지하고 구독자 목록을 관리·통지
Observer (구독자) 인터페이스통지받을 메서드의 규약을 정의
구체 Observer통지를 받아 각자 원하는 동작 수행(로깅, 통계, 알림 등)

10. Iterator Pattern — 원하는 순서로 마방진 값을 순회

행 우선, 열 우선, 대각선, 나선형 등 순회 방식이 여러 가지 필요할 수 있습니다. Iterator는 "어떻게 저장되어 있는가"와 "어떤 순서로 꺼내는가"를 분리해서, 새 순회 방식을 추가해도 MagicSquare 클래스는 전혀 건드리지 않습니다.

행동 패턴저장 구조와 순회 방식의 분리
의도(Intent) 컬렉션의 내부 표현(2차원 배열)을 노출하지 않으면서, 그 안의 원소들에 순차적으로 접근하는 방법을 제공한다.
// UML — Iterator
Java — SpiralIterator (나선형 순회)
Iterator<Integer> 인터페이스 구현
public class SpiralIterator implements Iterator<Integer> {
    private final int[][] magic;
    private int top=0, bottom, left=0, right, dir=0, r, c;  // 나선 경계 + 현재 위치

    public SpiralIterator(int[][] magic) {
        this.magic = magic;
        bottom = magic.length-1; right = magic[0].length-1;
        r = 0; c = 0;
    }
    @Override
    public boolean hasNext() { return top <= bottom && left <= right; }

    @Override
    public Integer next() {       // 방향 전환 로직으로 나선형 좌표를 계산
        int value = magic[r][c];
        // (좌표 갱신 로직 — 오른쪽→아래→왼쪽→위 순서로 방향 전환) 생략
        return value;
    }
}

public class OddMagicSquare extends MagicSquare implements Iterable<Integer> {
    @Override
    public Iterator<Integer> iterator() {  // 기본 순회는 행 우선
        return new RowIterator(magic);
    }
    public Iterator<Integer> spiralIterator() {
        return new SpiralIterator(magic);      // 원하는 방식은 별도 메서드로 제공
    }
}

// 사용 예 — for-each가 자동으로 iterator()를 호출
OddMagicSquare sq = new OddMagicSquare(5);
sq.make();
for (int v : sq) System.out.print(v + " ");          // 행 우선(기본 iterator())

Iterator<Integer> spiral = sq.spiralIterator();
while (spiral.hasNext()) System.out.print(spiral.next() + " ");  // 나선형
Iterator<T>Iterable<T>for-each 자동 연동
Python — 제너레이터로 훨씬 간결하게
__iter__ + yield — Iterator 클래스가 사실상 불필요
class OddMagicSquare(MagicSquare):
    def __iter__(self):          # 기본 순회 = 행 우선
        for row in self._magic:
            for v in row:
                yield v            # ★ yield 하나로 Iterator 클래스 전체를 대체

    def spiral(self):            # 나선형 순회는 별도 제너레이터 메서드로 제공
        m = self._magic
        top, bottom = 0, len(m) - 1
        left, right = 0, len(m[0]) - 1
        while top <= bottom and left <= right:
            for c in range(left, right + 1): yield m[top][c]
            for r in range(top + 1, bottom + 1): yield m[r][right]
            if top < bottom:
                for c in range(right - 1, left - 1, -1): yield m[bottom][c]
            if left < right:
                for r in range(bottom - 1, top, -1): yield m[r][left]
            top += 1; bottom -= 1; left += 1; right -= 1

    def diagonal(self):          # 대각선 순회 제너레이터도 추가 가능
        n = self._n
        for i in range(n):
            yield self._magic[i][i]
